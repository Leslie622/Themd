# 实时预览完美实施方案 v2 —— 对标 Typora（双引擎架构）

> **本版修订**：v1 文档把「完美」锚定在 CodeMirror 装饰层的天花板上，并将 Typora 的核心体验
> （渲染态直接编辑）列为非目标——方向错误。本版推翻重来：**实时预览视图更换引擎为
> ProseMirror 系（TipTap v3），实现真正的 Typora 式所见即所得**；CodeMirror 保留给
> 编辑/分屏视图，功能与源码语义零变化。
> 基线：v1 CM 装饰层（`src/lib/markdown-live-preview.ts`）作为过渡方案保留，新引擎达标后下线。

---

## 1. 目标定义

### 1.1 Typora 体验的三根支柱（本方案要对齐的东西）

1. **渲染态直接编辑**——文档默认就是渲染后的样子；在表格单元格里直接打字、双击公式直接改
   TeX、拖拽调整图片宽度；不存在「进源码 → 改 → 出来渲染」的两态切换
2. **聚焦显码**——光标所在的块临时显示 Markdown 源码标记，离开即恢复渲染（Typora 同款交互）
3. **富块常驻**——表格、公式、图表、代码块（内嵌专业编辑器）以真实组件形态活在文档流中

### 1.2 四条红线（每期验收前提）

| 红线 | 含义 | 保障机制 |
|---|---|---|
| **字节保真** | 未被用户编辑的块，保存时逐字节原样写回 | 块级 sourceMap 协议（§4） |
| **功能不倒退** | 现有 CM 编辑/分屏视图、全部命令、图片管线、写回同步不动 | 双引擎架构（§2），CM 原样保留 |
| **性能** | 万行笔记连续输入无可感卡顿；启动不被新依赖拖慢 | §9 |
| **输入法** | 中文 IME 全程可用（ProseMirror 的 contenteditable 是 IME 强项，此项从风险变优势） | P5 全输入法回归 |

### 1.3 非目标

- 不改 `Note.content` 字符串作为唯一事实来源的地位；不改 500ms 防抖/Ctrl+S/失焦冲刷写回管线
- 不改预览视图与导出管线（仍是 markdown-it 全文渲染）
- 不自研 contenteditable 引擎（Typora 走了十年，不可复制）

## 2. 核心架构决策：双引擎

```text
┌─ 顶栏视图组 ─────────────────────────────────────────────┐
│  edit      split              live            preview    │
│  ┌───────┐ ┌───────┬───────┐ ┌────────────┐ ┌─────────┐ │
│  │ CM6   │ │ CM6   │ md-it │ │ TipTap v3  │ │ md-it   │ │
│  │ 源码  │ │ 源码  │ 预览  │ │ PM 渲染态  │ │ 预览    │ │
│  └───────┘ └───────┴───────┘ └────────────┘ └─────────┘ │
└──────────────────────────────────────────────────────────┘
        所有视图读写同一个 Note.content（Markdown 字符串）
   → updateNote → 500ms 防抖 → Rust 原子写 → watcher（既有管线零改动）
```

**为什么这个架构同时满足三条线：**

- **Typora 体验**：live 视图换 ProseMirror，渲染态直接编辑是 PM 的本职——表格/公式/图片是
  **结构节点**而非文本流，直接编辑、拖拽、原子化操作都是一等公民
- **功能不变**：编辑/分屏视图的 CodeMirror 一行不改。上一轮的问题「PM 能否复刻 CM 全部功能」
  在此架构下**不需要成立**——CM 还在，live 视图单独补齐自己的功能对等面（§6）
- **字节保真**：PM 只在 live 视图内持有文档模型；落盘仍是 content 字符串，未编辑块经
  sourceMap 原文写回（§4）。watcher 回声抑制、冲突弹窗、树=磁盘语义全部不感知引擎切换

**v1 CM 装饰层的去留**：live 视图切到 PM 后，v1 代码休眠保留一个过渡期（偏好开关
`liveEngine: 'prosemirror' | 'codemirror'`，默认前者），PM 引擎过全部红线后删除。

## 3. 引擎选型

| 候选 | 结论 | 理由 |
|---|---|---|
| **TipTap v3 + `@tiptap/markdown`** | ✅ 采用 | 2025-10 起有**官方第一方** Markdown 双向支持：解析、序列化、多方言、**每扩展可自定义序列化规则**、MarkdownManager 支持纯客户端序列化（块级保真协议的钩子齐了）。React 绑定第一方（本项目 React 19）。schema/Node/NodeView 完全可控，代码块节点内嵌 CM6 是成熟模式 |
| Milkdown + Crepe | 备选 | 活跃维护、Typora 式定位相近；但 Crepe 自带整套 UI（工具栏/slash 菜单），与本项目「shadcn 官方组件硬规范」正面冲突，剥离成本高于自建；基于 remark（第三套 markdown 解析器）；PM 版本被内部 re-export 锁死，定制受限 |
| Muya（MarkText 引擎） | ❌ 否决 | 最接近 Typora 的开源实现，但 2022–2026 停滞四年、2026-05 刚复活，API 不稳定，不可作为长期依赖 |
| 自研 contenteditable | ❌ 否决 | 十年工程 |

TipTap 与硬规范的相容性：TipTap 是编辑引擎不是 UI 组件库；live 视图的右键菜单/BubbleMenu/
表格工具条等一切 UI 面**继续用现有 shadcn 组件**（ContextMenu/Button/Tooltip）拼装，TipTap
只提供编辑表面与 NodeView 挂载点。

## 4. 字节保真协议（本方案最核心的一章）

### 4.1 问题

PM 文档是结构模型，Markdown 只是序列化出口。整文档 parse→serialize 往返必然产生规范化
改写（`*`→`**`、Setext→ATX、空白重排）。而本项目的 watcher 回声抑制靠
「磁盘内容 == lastWritten」逐字节比较——**任何静默改写 = 编辑中误弹冲突窗**。

### 4.2 契约

> **未编辑的块逐字节原样写回；只有用户真正动过的块才重新序列化。**
> 这是 Typora「逐块 parse/serialize」思路在 PM 上的等价物，也是整个迁移成立的前提。

### 4.3 实现：块级 sourceMap + dirty 跟踪（纯函数，进 domain 层）

```text
parse 阶段（content → PM doc）:
  1. 块切分:按空行 + 围栏感知把 content 切成顶层块原文数组
    ( fenced code 内的空行不切分;front matter 整块;表格整块 )
  2. 每块单独 parse 成 PM 节点,拼装文档;同时记录
     BlockRecord { id, from, to, sourceText, dirty: false }

编辑阶段（PM transaction 拦截）:
  3. appendTransaction 监听 tr.changedRange → 标记命中的 BlockRecord.dirty = true
    ( 跨块操作(如整段删除、合并段落)标记全部受影响块 )

serialize 阶段（content 出口,防抖触发）:
  4. 遍历 BlockRecord:
     !dirty → 直接吐 sourceText
     dirty  → 该块 PM 子树交 @tiptap/markdown 序列化(单块序列化)
  5. 块间连接符(空行数量)不在块内,单独保序:连接符跟随左侧块的原文,
     新增块用标准 "\n\n"
```

### 4.4 风格档案（把 dirty 块的序列化失真压到最低）

用户原文风格与序列化器默认输出不一致时，编辑过的块会产生「非语义 diff」。用**风格档案**
吸收：parse 时统计全文的列表标记（`-` vs `*` vs `+`）、强调标记（`**` vs `__`）、标题风格
（ATX vs Setext）偏好，serialize 时把档案注入自定义序列化规则
（`@tiptap/markdown` 的 per-extension 规则覆盖点）。用户全篇用 `*`，编辑一块后写回的还是 `*`。

### 4.5 守门测试（红线回归，P0 就建）

- **往返零 diff 测试**：语料库（用户真实笔记样本 + 边缘 case：嵌套列表缩进、HTML 块、
  紧凑/宽松列表、CRLF、BOM、无结尾换行）跑「parse → 不编辑 → serialize」，断言逐字节相等
- **单块编辑测试**：语料库每篇只编辑第 N 块，断言 diff 仅限该块
- 该测试进 CI，是每次动 schema/序列化规则的强制门禁

## 5. 数据流与同步边界

```text
进入 live 视图 / 切换活动笔记:
  content → parse(块切分+sourceMap) → PM doc → TipTap

键入(渲染态):
  PM tr → dirty 标记 → onUpdate → serialize(§4.3) → content 字符串
  → updateNote → 500ms 防抖 → Rust 原子写(既有管线,零改动)

外部改动(watcher):
  与 CM 视图同语义 —— 干净笔记整文档重新 parse(live 状态重置,
  等价于 CM 的 remount);有未写回编辑仍走 fs-conflict 二选一

undo/redo:
  PM 自带历史(块级);跨视图切换历史不延续(与 CM 现状同语义)

Ctrl+S / 失焦 flush / 托盘退出:
  flush 时强制 serialize 一次确保 content 最新(防抖未到点的情况)
```

边界注意：`onUpdate` 里只做 dirty 序列化，**不做**整文档重 parse（否则光标/历史丢失）；
活动笔记切换用 `key` 重挂载（与 CM 现行 `key={active.id}` 一致）。

## 7. 富块设计（Typora 对齐的主战场）

- **表格**：TipTap 表格扩展（结构化行列、Tab 导航、行列增删菜单用 shadcn 拼装）。
  序列化按 sourceMap 原文（未编辑时对齐列宽保持原文；编辑过用风格档案重排列宽）
- **数学公式**：行内 `$…$`/块级 `$$…$$` 自定义 Node；NodeView 用 KaTeX `renderToString`
  （`throwOnError:false`）；聚焦显 TeX 源码编辑。**预览/导出侧同步补** `@mdit/plugin-katex`
  （现状预览也不渲染公式,一次补齐三面）
- **mermaid**：块级 NodeView,动态 import + 视口懒渲染 + 结果缓存；预览侧 mdit 异步 rule 同步补
- **代码块**：自定义 NodeView 内嵌 **CodeMirror 6**（Typora/Milkdown 同款做法）——现有 CM
  高亮配置、搜索、字体偏好全部复用,这正好是 CM 强项的保留地
- **任务列表**：checkbox 即节点属性,点击即写回(比 v1 的 regex 替换干净)
- **图片**：NodeView 原生支持选中后拖拽手柄调宽;写回 `![alt](src =300x)` 尺寸后缀
  （markdown-it 原生支持,预览侧已兼容;P4 启用前扫描存量笔记确认无误伤）
- **front matter**：折叠为状态条 NodeView,点击展开
- **聚焦显码**：光标所在块的 NodeView 加 `prose-focused` 态显示 markdown 源标记
  （对齐 Typora;各节点按需实现,段落/标题/强调优先）

## 8. 主题与排版（live 视图的独特机会）

live 视图是 Typora 式**单排版域**——终于可以让编辑区直接消费笔记主题：

- 编辑器容器注入 `compileTokens` 的 `--t-*` CSS 变量（与 PreviewPane 同源,含单篇笔记主题覆盖）
- 正文排版复用 `theme-base.css` 的 `.themd-prose` 规则（live 容器挂同类名）,标题/引用/表格
  与预览、导出观感一致
- UI 面(菜单/工具条)仍是 shadcn 令牌;代码块内嵌 CM 保持编辑器配色

这一期做完,「编辑时看到的」与「导出得到的」第一次真正同源。

## 9. 性能

- **超长行**：v1 的死穴在 PM 架构下自然消失——base64 图片/超长 URL 存节点属性,不进文本流
- **大文档**：TipTap/PM 按节点渲染,万行段落文档天然分块;表格/公式 NodeView 结果 LRU 缓存
- **启动**：TipTap 核心 + 用到的扩展静态导入（~150KB gzip 级）,mermaid/KaTeX 字体动态 import
- **基准**（P5 门禁）：万行笔记键入 P95 < 16ms/帧;切笔记 parse < 150ms;启动增量 < 300ms

## 10. 双引擎一致性纪律

live 渲染出自 PM，预览/导出出自 markdown-it——两个引擎对边缘语法（嵌套列表缩进、HTML 块、
引用内列表）可能有解析差异。纪律：

1. PM schema 支持的语法面**严格对齐** markdown-it 已启用的子集（html:true、breaks:true、
   linkify、typographer、GFM 表格/任务/删除线）
2. 建双引擎差异样本库：同一批 case 分别过 PM parse/serialize 与 md.render,快照对比,CI 常驻
3. 用户视角兜底：live 看到的与预览如有分歧,以预览/导出为准修 PM 侧

## 12. 风险与回退

| 风险 | 概率 | 缓解 |
|---|---|---|
| 序列化保真覆盖不全（冷门语法） | 中 | P0 守门测试先行;语料库拿用户真实笔记;漏网块退化为「整块标 dirty」(改写可见但不静默) |
| TipTap 版本演进破坏序列化规则 | 低 | 锁 minor;@tiptap/markdown 是官方第一方,自定义规则是公开 API |
| 工期比预期长 | 中 | P1–P3 有 v1 兜底,随时可停在任一期发布;live 视图引擎开关一键回 CM 装饰层 |
| 双引擎解析差异 | 中 | §10 样本库 + 以预览侧为准 |
| 包体/启动 | 低 | TipTap 核心静态(~150KB gzip 级),KaTeX/mermaid 动态 |
| IME 意外 | 低 | PM contenteditable 是 IME 强项;P5 全输入法回归兜底 |
