## 1. 最终目标(用户定,缺一不可)

1. **单一真相**——渲染出来的东西一模一样,一丝偏差都不能有。
   同一篇笔记在预览视图、实时编辑视图、主题工厂样例里看到的样式必须完全相同。
2. **样式可移植**——用户在本应用调出的一套 MD 样式,可以应用到任何标准 Markdown 上
   (Typora / VSCode / GitHub 等),这是产品初衷。
3. **导出全量还原**——导出的 HTML、PDF 与预览时的观感完全一致。

## 2. 现状与问题

### 2.1 双引擎现状

| 视图/链路 | 引擎 | 角色 |
|---|---|---|
| 实时预览编辑(Typora 式) | TipTap(ProseMirror) | 编辑器,光标/选区/撤销/即时输入 |

主题工厂三个标签页里,「专注样例 / 全内容样例」走 markdown-it,「导入笔记」走 TipTap。

## 3. 从目标推导:真相是结构契约,不是引擎

三个目标翻译成技术语言:

- **目标 1 拆开是两个条件**:两处渲染一模一样 = **DOM 结构一致 × 同一份 CSS 命中**。
  CSS 相同但结构差一层 div(任务列表 bug 正是此类),或结构相同但选择器只在一边命中,
  都会破坏它。
- **目标 2 是最强约束**:CSS 贴到 Typora/VSCode/GitHub 要能用 →
  CSS 必须命中**规范 Markdown 结构**(CommonMark/GFM 渲染产物)。
  不能指望别家渲染器生成 `li > div > p`、`data-type="taskItem"` 这类私有结构。
- **目标 3 是推论**:导出与预览走同一函数、吐出同样字节,目标自动成立,不需要「努力达成」。

结论:

> **单一真相 = 一个函数 C(笔记) → 规范 HTML。**
> 规范 = CommonMark/GFM 结构 + 超规范扩展(提示块/任务列表/数学/mermaid)的本家结构定义。
> 引擎只是「谁能稳定产出这个 HTML」的选型题,不是目标本身。

**对第一版方案的方向性修正**:第一版以「全 TipTap」为真相。若照执行,三面会统一成
TipTap **原生**结构——目标 1 达成,目标 2 悄悄报废:可移植 CSS 命不中私有结构,
而 taskItem 的 div 包装正是现存 bug 的结构根源。统一了 HTML,引擎只是顺手的选型题。

## 4. 四条不变量(契约的运行形态)

| # | 不变量 | 内容 | 直接支撑 |
|---|---|---|---|
| I1 | 全消费方同一管线 | 预览、实时编辑、工厂样例、导出,全部消费同一个函数 C | 目标 1 |
| I2 | CSS 零私有钩子 | theme-base.css 只写命中规范结构的选择器,私有结构钩子数量为零 | 目标 2 |
| I3 | 导出即同一函数 | 导出 = C 输出 + 内联令牌 + theme-base.css 原文,同字节 | 目标 3 |
| I4 | 编辑镀层不参与布局 | 编辑面 = 规范 HTML + 零布局镀层:光标/选区/拖拽手柄/checkbox 交互用绝对定位、装饰层叠加,禁止往文档流塞额外元素 | 目标 1(编辑面) |

I4 是「实时编辑和预览一模一样」的结构性保障——不靠事后对齐,
靠镀层在物理上无法改变布局。

## 5. 引擎选型

需要一个东西,同时满足:**能编辑**(实时编辑是产品核心体验)+
**输出可被约束成任意结构**(I1/I2)。

| 候选 | 判定 |
|---|---|
| markdown-it | 输出天然规范,但**不能编辑**——只能当静态渲染器,编辑面仍需另找引擎,回到两个真相 |
| TipTap/ProseMirror | 能编辑;结构由 schema 的 toDOM 决定,**完全可定制**——可驯化成只吐规范结构。**选定** |
| Milkdown(markdown 优先的 PM 封装) | 理念契合,但等于重写编辑层;且它没有取消结构契约这堵承重墙,自定义节点(callout/live-image/数学)照样自写。收益边际,否 |
| 自研 Typora 式编辑器 | 成本不可行,否 |

结论落点与第一版碰巧相同(TipTap 系),但承重理由不同:
TipTap 是唯一「既能编辑、又能被约束成规范结构」的现成件。

**markdown-it 的新角色:迁移期裁判(出题人)。** 它输出天然规范 →
用它冻结金样语料的期望 HTML 作为**规范记录**;TipTap 每驯化一个节点拿它对答案;
全部对上后从生产链退役,冻结语料留下当规范本体。
它不是被打败的旧引擎,是留下标准答案后功成身退的出题人。

## 6. 技术核实:两条战线

### 6.1 输出线(toDOM 规范化)——逐节点对齐规范

| 事项 | 状态 |
|---|---|
| mermaid 图表 | 已解:live 侧 mermaid-render 按代码哈希缓存 SVG;静态管线 = generateHTML + 缓存后处理。注意 mermaid 异步而 generateHTML 同步,导出前必须预热渲染 |
| 图片路径(asset:// / 相对路径) | 已解:live-image 已接 resolveImageSrcSync,渲染期解析 |
| 数学公式 KaTeX | 已解:math-node 已有;KaTeX renderToString 是同步的,逻辑进 toDOM |
| GFM 提示块 | 已解:callout-blockquote 已是三面渲染模式 |
| 任务列表结构 | **要补**:taskItem 去 div 包装、checkbox 用标准 `<input type="checkbox">`(目标 2 的关键用例) |
| 标题 slug 锚点 | **要补**:TipTap 扩展给 heading 注入 id(十几行),消费方是导出 HTML 与锚点跳转 |
| 紧凑/宽松列表 | **要决策**:CommonMark 本身两种结构(宽松 `li > p` / 紧凑裸文本)。CSS 规约必须两种结构下观感一致(间距尽量落 li 层而非 `li > p` 层),决策写入契约 |
| 静态渲染性能 | **要补**:generateHTML 比 md.render 慢,预览加内容哈希缓存;大文档基准纳入验收 |
| NodeView 自足性 | **要审**:generateHTML 不执行 NodeView——凡视觉依赖 NodeView 的节点,toDOM 必须自足(视觉逻辑进 toDOM 或共享渲染模块)。系统性过一遍,不止数学公式一处 |

### 6.2 输入线(解析保真)——第一版漏掉的战线

markdown → PM doc 这一步,schema 不认识的东西在**打开文件时就丢**
(内嵌 HTML、HTML 实体、行内 `<b>`/`<u>`、脚注……)。
契约必须**双向**:输入无损策略 + 语料包含保真用例。

**解析保真政策(已拍板,2026-11-03)**:选 **① raw HTML 节点原样保真**——
schema 不认识的内嵌 HTML 进 raw HTML 节点,原样进文档流,导出时原样吐出。
理由:用户的笔记可能来自任何地方(Typora/Obsidian 迁移),静默丢内容是数据丢失,
与目标 3「全量还原」隐性冲突;+1 天买断数据安全。

## 7. 验收体系:金样语料 + 字符串精确相等

结构契约的红利:验收可做到**字节级精确**,不用拿模糊工具量所有面。
**已落地**:契约正文 [渲染结构契约.md](渲染结构契约.md);
语料与冻结期望 `src/modules/rendering/golden/`(corpus.md / corpus.expected.html),
守门测试 `golden-corpus.test.ts` 随 `npm run test` 常驻运行——第 1 步「写契约」完成。

- **金样语料**:全元素覆盖文稿——标题六级/段落/行内五件套/链接/图片/
  有序无序列表(**紧凑/宽松两种形态**)/嵌套列表/任务列表/表格(含对齐)/引用/
  提示块五类/代码块与行内代码/数学/mermaid/分隔线/边界用例/解析保真用例。
- **静态面验收(预览/工厂/导出)= 字符串相等**:`generateHTML(parse(语料))`
  与冻结 HTML 逐字节相等。确定性、零误报、CI 友好,不起浏览器。
- **编辑面验收 = computed-style diff**:唯一 DOM 合法偏离规范结构的地方(I4 镀层),
  逐元素 diff 字体/字号/颜色/间距/边框/圆角。范围从「全库」缩到「一个面」。
  **已落地**:`golden/style-parity-harness.ts`(dev 专用模块,同页面双渲染
  静态/编辑面 + 按规范选择器配对逐元素 diff);运行方式:dev server 起着时
  浏览器控制台 `await import('/src/modules/rendering/golden/style-parity-harness.ts').then(m => m.runStyleParity())`。
  **2026-11-03 终态:143 对元素,样式差异 0,结构差异 0**;
  永久豁免仅 2 类 I4 固有(CM 内部行结构、raw HTML 源码态显示);
  折行行为由几何探针把关(长行横向溢出,两侧一致)。
- **参照系是契约,不是 markdown-it 现状**:拉平中若发现 md-it 侧本来就不符合
  主题令牌定义,该改主题;若发现 md-it 行为属于规范外怪癖,显式修订单边入契约,
  不留隐性偏差。

## 10. 风险与对策

| 风险 | 对策 |
|---|---|
| 迁移期回归(6 个消费方) | 每步切换跑字符串相等;语料即回归基线 |
| 迁移期开发纪律 | **冻结 markdown-it 侧新特性**;迁移期内新渲染特性默认只写 TipTap 侧 |
| NodeView 镀层违规(往文档流塞元素) | I4 铁律 + 编辑面 computed-style harness 拦截 |
| toDOM 视觉不自足 | §6.1 NodeView 自足性审查,视觉逻辑下沉 toDOM 或共享模块 |
| mermaid 导出时缓存未命中 | 导出流程先预热渲染再生成(异步等待) |
| generateHTML 性能 | 内容哈希缓存;大文档预览基准纳入第 2 步验收 |
| 工厂「选择元素」依赖 DOM 映射 | 第 4 步切换时同步重写映射表(规范结构对齐后映射表反而更稳) |
| CodeMirror 退役是用户可感知变更(设置项消失) | 搭车清理合理,但在变更说明中向用户显式交代,不计入「零视觉变化」承诺 |
